## 2. 점주 요약 대시보드 — 추천: 예(1순위)

### 현재 상태
- 점주 웹의 숫자는 `오늘 방문 N건` 하나뿐이다(merchant.mjs:776). 이 값은 목록 길이라서 취소 건까지 포함한다.
- 점주가 읽을 수 있는 통계 API가 없다.

### 개선 목표
첫 화면 위에 "가게 현황" 카드를 둔다.
- 방문
  - 오늘 / 이번 주
  - 지난주 대비 증감: 비교가 공정할 때만 보인다
  - 최근 7일 막대
  - 누적
- 이번 주 쿠폰 사용
- 재방문 고객: 서로 다른 날 2번 이상 방문
- 캠페인 상태와 고객 앱 공개 여부

### 필요한 변경
- DB: 없음.
- API: `GET /api/web/merchant/merchants/:id/overview`
  - 권한은 기존 `CONFIRM_VISIT`. 활성 점주·직원 모두 볼 수 있다.
  - 방문은 배지·마일리지와 같은 "세어지는 방문" 기준으로 센다(`countedVisitFilterSql`). 하루 1회, 직원 본인 적립 제외, 체험 점포 제외.
  - 주는 KST 월요일에 시작한다.
- 점주 웹: 카드 칸.
  - 방문 카드(오늘·이번 주·최근 7일·누적)를 누르면 `#merchant-visit-title`(오늘 방문 기록 목록의 제목)로 간다.
  - 쿠폰 카드를 누르면 `#merchant-redemption-title`로 간다.
  - 캠페인 카드는 상태와 "변경은 운영팀에 요청" 안내만 보인다.
- 비교 규칙: 가게 `published_at`이 지난주 시작보다 늦으면 증감을 숨긴다. 이번 주는 끝나지 않았으므로 지난주 전체가 아니라 지난주 같은 시각까지(월요일 00:00 KST부터 지금에서 7일 전 시각까지)와 비교한다.

### 난이도·영향
- 난이도: 하~중.
- 영향 범위: API(읽기 전용 라우트), 점주 웹, 시험. 앱 배포는 필요 없고 서버·웹 배포만 하면 된다.

## 3. 점포 오픈 준비 체크리스트 — 추천: 예(2와 같은 칸)

### 현재 상태
- 노출 조건은 다음 일곱 개다(merchant-catalog.ts:58-68).
  1. 가게 `ACTIVE`
  2. 캠페인 `ACTIVE`
  3. 캠페인 `is_public`
  4. 시작 ≤ 지금
  5. 지금 < 종료
  6. 체험 점포 행 없음
  7. 목표가 정확히 {1,3,5}
- 공개 요건은 메뉴 1개 이상·영업시간·주소(store-go-live-rules.ts:47-56)다.
- 점주에게는 이 중 아무것도 보이지 않는다.

### 개선 목표
6단계 상태와 "고객 앱 공개까지 N단계 남았습니다" 문구를 보인다.

| 단계 | 판정 | 상태 |
| --- | --- | --- |
| 1. 가게 기본 정보 | 이름·도로명 주소·영업시간 | 완료 / 설정 필요 |
| 2. 메뉴 | `menu_items` 1개 이상(가게 사진 칸은 없어 제외) | 완료 / 설정 필요 |
| 3. 점주·직원 | 활성 점주 1명 이상(직원 수는 참고로 표시) | 완료 / 확인 필요 |
| 4. 방문 보상 | 캠페인 목표 {1,3,5}와 수집품 게시 연결 | 완료 / 설정 필요 |
| 5. 캠페인 | 공개·기간 안 | 완료 / 공개 예정(시작 전) / 확인 필요(일시정지·종료·초안) |
| 6. 고객 앱 공개 | 위 7조건 모두 참 | 완료 / 승인 대기(가게가 `PAUSED`인데 1~3 완료) |

### 필요한 변경
- 2와 같은 API 응답의 `readiness`로 내려준다.
- 판정은 순수 함수 하나에 모은다. 단위 시험에 더해, 공개 목록 SQL과 결과가 같은지 확인하는 통합 시험을 둔다.
- 쿠폰 오퍼는 플랫폼 단위 설정(D-042·D-054)이므로 가게 단계가 아니라 안내 문구로만 보인다.

### 난이도·영향
- 난이도: 중.
- 영향 범위: API, 점주 웹.

## 4. 가게 검색 강화 — 추천: 예

1. **메뉴 검색**
   - 하는 일: 모바일 `filterMerchants`(merchant/filter-merchants.ts)에 메뉴 이름을 더하고, 자리표시 글을 "이름·메뉴·주소로 찾기"로 바꾼다.
   - 변경 범위: 모바일만. 메뉴는 이미 응답에 있다.
   - 메뉴 설명은 칸이 없어 이번에 제외한다.
   - 난이도: 하.
2. **보상 기준 필터 칩**
   - 칩 종류: "보상까지 1번", "안 가 본 곳", "가 본 곳", "쿠폰 쓸 수 있는 곳".
   - 데이터: 도감과 같은 `buildMerchantGoals` 결과(앱 안 정의 일치)와 `/me/badges`의 미사용 쿠폰 `merchantId`를 쓴다.
   - 로그인했을 때만 보인다.
   - 변경 범위: 모바일만. 난이도: 중하.
3. **업종 필터**
   - 하는 일: 공개 목록 SQL과 `PublicMerchant`에 `category`(없을 수 있음)를 더하고, 목록에 있는 업종만 칩으로 보인다.
   - 변경 범위: 마이그레이션 없음.
   - 실제 점포의 업종 값은 운영 관리자 웹에서 채운다(데이터 작업).
   - 난이도: 하.
4. **추후 확장**: 태그 집계가 공개 목록에 실리므로, 태그 칩 필터는 데이터가 쌓인 뒤 칩 몇 개를 더하면 된다.

## 5. 인증 방문자 가게 특징 태그 — 추천: 예(새 핵심 기능, 민감 경로)

### 현재 상태
- 태그·리뷰·평점 테이블과 API가 없다.
- 자유 텍스트는 친구 별명뿐이다.

### 개선 목표
- 방문 완료 화면에서 고르는 것은 선택 사항이다. 태그는 아래 8종 중 최대 3개다.
  - 혼밥하기 좋아요
  - 포장이 편해요
  - 양이 넉넉해요
  - 조용해서 대화하기 좋아요
  - 친절해요
  - 가성비가 좋아요
  - 학생이 가기 좋아요
  - 디저트가 좋아요
- 가게 상세에 "방문자들이 고른 특징 · N명" 집계를 보인다.
- 상세에서 내 선택을 바꿀 수 있다.

### 필요한 변경
- **DB**
  - `merchant_visitor_tags(customer_account_id, merchant_id, tags text[], updated_at)`
    - PK `(customer_account_id, merchant_id)`: 중복 집계가 없고 수정은 덮어쓰기다.
    - CHECK: 허용 코드의 부분집합이고 개수는 3 이하.
    - 인덱스: `(merchant_id)`.
  - 계정 삭제 처리기에 행 삭제를 더한다(전수 컬럼 시험이 강제한다).
- **API**
  - `PUT /merchants/:id/visitor-tags`
    - 자격: 그 가게에 VALID 방문이 1회 이상 있을 것. 직원 본인 적립과 체험 점포는 제외한다.
    - 빈 배열을 보내면 선택이 삭제된다.
  - `GET /me/visitor-tags/:merchantId`
  - 공개 목록의 `visitorTags: [{code, count}]`
    - 실제 점포는 3명 이상인 태그만 보인다(소수 노출 방지).
    - 시연 가상 점포(`is_demo`)는 1명부터 보인다.
- **모바일**: 방문 완료 카드의 선택 칩, 상세의 집계와 수정, 목록 카드의 대표 태그 1개.
- **점주 웹**: 우리 가게 태그 집계. 3명 기준을 똑같이 적용한다.

### 난이도·영향
- 난이도: 중상.
- 영향 범위: DB·API·모바일·점주 웹·계정 삭제·개인정보 고지 확인.
- 민감 경로(DB 스키마)이므로 sonnet·opus 교차 리뷰 2개를 받는다.
- 운영 배포 전에 호환성 증거를 남긴다(테이블 추가만 하므로 뒤 호환이다).

## 6. 점주에게 전달하는 고객 의견 — 추천: 축소해서 예

- 현재 상태: 없음.
- 자유 텍스트를 넣으면 다음 비용이 든다.
  - 개인정보·악성 문구 필터(D-051 필터 재사용 가능)
  - 신고·차단 같은 운영 부담
  - 개인정보 처리방침에 새 수집 항목 추가와 재동의
  - 결선 전 위험이 크다.
- 제안: **선택형 "사장님께 바라는 점"**
  - 항목: 혼밥 메뉴 / 맵기 표시 / 메뉴 사진 더 / 학생 할인 시간 / 영업시간 안내. 최대 2개.
  - 태그와 같은 테이블의 `suggestions text[]` 칸을 쓰고, 화면에서도 태그와 같은 순간에 고른다.
  - 점주 웹에서만 "바라는 점 · N명"으로 보인다. 공개하지 않는다.
- 자유 텍스트는 결선 뒤로 미룬다.

## 9. 시연 전부 체험 (묶음 E, 소유자 결정 2026-10-03)

소유자 지시: "시연용은 뽑기권 그냥 여러 개 줄 수 있냐? 마일리지라던지 뽑기권이라던지 시연은 그냥 전부다 되게 만들어줘 전부다 테스트 할 수 있게".
운영 API·DB·앱의 보상 규칙(D-004·D-006·D-063)은 그대로 둔다. 바뀌는 것은 시연 서버의 시연 전용 경로뿐이다.

- 마일리지
  - 시연 서버의 마일리지 상점은 `earned`에 시연 체험분(상수, 예: 100000)을 더한다.
  - 응답에 `showcaseBonus`를 따로 실어, 앱이 "시연 체험 마일리지 포함"이라고 표시할 수 있게 한다.
  - 시연에서는 재뽑기 횟수 제한을 넉넉하게 둔다.
- 테스트 방문
  - "테스트 방문 만들기"는 같은 가게에서 아직 세어지지 않은 가장 최근 한국 날짜(오늘부터 거꾸로, 최대 30일 전까지)를 방문일로 쓴다.
  - 그래서 연속으로 누르면 1·3·5회가 각각 따로 세어져 실버·골드와 배지·상자까지 이어진다.
  - 이 날짜 바꿔 넣기는 시연 테스트 발급자가 만든 슬롯에만 적용한다. 일반 방문 확인 경로는 지금처럼 "지금"을 쓴다.
  - 시연 테스트 방문의 시간당 제한은 10회에서 60회로 올린다.
- 운영 API에는 여전히 테스트 방문 경로와 체험 마일리지가 없다. 이것을 시험으로 고정한다.
- 결정 기록: `docs/DECISIONS.md`에 새 D 항목으로 남긴다(시연 한정 보상 체험 완화).
