## D-086 첫 코인 "내 공간에 놓기" 제안 (Issue #412, 2026-10-08)

소유자 2026-10-08 방향(첫 수집품 획득 순간에 "첫 코인을 내 공간에 놓아볼까요?", 공간 공개는 별도 동의)에 따라 봉투 끝 화면에 제안을 넣었다(`PROPOSED`). 조건은 모두 충족해야 한다. (1) 이 봉투가 준 코인 말고는 도감에 아무것도 없는 첫 수집품이다. (2) 서버에서 지금 읽은 내 공간이 한 번도 저장하지 않은 상태(revision 0)이고 진열·코인·가구가 비어 있다. (3) 공간 공개 범위가 `PRIVATE`이다. (4) 공간·공개 범위·도감 세 조회가 모두 성공했다. 하나라도 실패하거나 알 수 없으면 제안하지 않는다. 화면이 받은 도감은 대역일 수 있어 조회를 건너뛰는 데만 쓴다.

"놓기"는 저장 직전에 공개 범위를 다시 읽어 `PRIVATE`이 아니면 저장하지 않고 안내만 한다. 저장은 제안 때의 revision으로 하고, 버전 충돌이면 공간을 다시 읽어 코인이 이미 놓였으면 성공으로, 아니면 "공간이 바뀌었어요"로 처리한다. 앱은 공개 범위를 쓰지 않는다. 공개는 `ROOM_CONSENT_REQUIRED`와 별도 동의 흐름 그대로이며 첫 전시를 자동 공개하지 않는다. 미리보기는 "기본 선반(기본 제공)"으로 소유한 코인과 구분하고, 소유하지 않은 가구는 그리지 않는다.

남는 작은 창: 서버 `saveStudio`(`apps/api/src/postgres/play.ts`)는 공개 범위를 조건으로 받지 않고, 공개 범위 변경은 공간 revision을 올리지 않는다. 그래서 공개 범위를 다시 읽은 뒤 저장되기까지의 왕복 한 번 사이에 다른 기기에서 공개 범위를 바꾸면, 방금 놓은 코인이 바뀐 범위에 보일 수 있다. 서버에 원자적 조건을 만들려면 API 변경이 필요해 이번 범위에서 하지 않았고, 사용자가 공개 범위를 이미 바꾼 계정에서 첫 코인을 받는 순간에만 생기는 좁은 경우다.

## D-087 가게 사실 표시 원칙: 서버가 지키는 것만 규칙으로 쓴다 (Issue #412, 2026-10-08)

가게 카드·상세에서 "미확인"을 반복하지 않으면서 헷갈리는 순간을 줄이는 원칙을 정했다(`PROPOSED`). 원칙: 서버가 실제로 거절하거나 무시하는 것만 규칙으로 쓰고, 화면에 표시될 뿐 서버가 강제하지 않는 신호는 단서(caveat)로 쓴다.

방문 인정 조건은 `SERVER_RULE`(앱이 확인)과 `STORE_SETTING`(가게에서 확인)으로 나눠 보인다. 진행 중인 캠페인이 있어야 한다, 직원이 1회 방문 코드를 발급해야 한다, 같은 가게는 한국 시간 하루 한 번이다, 방문 코드는 15분 안에 확정한다는 서버 규칙이다(코드 유효 시간은 `claim-slot-service.ts`의 값과 같아야 하며 시험이 어긋남을 잡는다). 최소 이용 금액과 영업 시간은 가게가 정한 값을 직원이 확인하므로 앱이 강제한다고 쓰지 않는다. 시연 점포는 "테스트 방문 만들기"로 체험하므로 직원 확인과 하루 한 번 규칙이 적용되지 않는다고 따로 쓴다. 캠페인이 없거나 진행 중이 아닐 때만 "받을 수 없다"고 말한다(서버가 방문을 거절한다). 접수 가득 참·마감, 보상 소진·미운영·그림 없음은 서버가 거절하지 않으므로 "표시상 ~이고 방문 확인 결과로 정해져요"라는 단서로 쓴다.

표시는 세 층이다. 핵심(이름·층·거리)을 먼저 보이고, 방문 결정에 중요한 영업 상태·마지막 주문(또는 임시 안내)·보상·최소 이용은 알 수 없어도 항상 보이되(경고 톤) "정보 없음"으로 숨기지 않는다. 그 밖의 부족한 정보(위치·입구·층·사진·요일별 시간)는 목록에서는 "일부 가게는 위치·입구 정보가 아직 없어요" 한 줄로, 상세에서는 "정보가 더 필요한 항목" 한 블록으로 모은다. 시연 점포의 자리 표시 주소는 줄에서 뺀다("시연 데이터" 표시는 유지). 사진이 없으면 가게 문장(crest)을 쓴다. 접근성 이름에는 전체 내용을 유지한다.

## D-088 API 서버 구조 규칙: routes·http·이름 붙은 deps (Issue #412 트랙 T1, 2026-10-08)

약 2,600줄이던 `apps/api/src/server.ts`를 동작 변경 없이 나눴고 그 구조를 규칙으로 정한다(`PROPOSED`, 에이전트 구현 선택). 소유자 결정 A에 따라 배포하지 않았다.

규칙: (1) 경로는 `src/routes/<영역>.ts`의 `handleXxx(ctx): Promise<boolean>`로 쓴다. `true`는 응답을 냈다는 뜻, `false`는 다음 처리기로 넘긴다는 뜻이며, `server.ts`가 고정된 순서로 부르므로 이 순서가 곧 경로 우선순위다. 경로 모듈은 `server.ts`를 가져오지 않는다. (2) 요청·응답 도우미(본문 읽기, 헤더·쿠키, 오류 응답, 제한기, QR)는 `src/http/*`에 둔다. (3) `createApiServer`는 위치 인자 대신 이름 붙은 `ApiDeps`(`src/api-deps.ts`) 하나를 받는다. 시작 코드의 `Required<ApiDeps>`와 `Required<ExperienceServices>`가 키 누락을 컴파일에서 잡는다(`exactOptionalPropertyTypes`라 값은 `undefined`여도 키는 반드시 적는다). 기본값(`trustProxyClientIp`, `webWwwEnabled`, `experienceServices`)은 `createApiServer`가 받은 deps를 복사해 `Object.freeze`하면서 한 번만 정하고, 런타임과 경로 처리기는 그 객체를 `??` 없이 읽는다. (4) 제한기·계정 해석 래퍼·동의/스캔 확인은 `createApiRuntime(deps)`가 서버 인스턴스마다 만든다. 모듈 전역 상태는 두지 않는다.

시험 도우미: 위치 인자로 서비스 몇 개만 채워 서버를 만들던 옛 모양은 시험 전용 덮개(`src/server-test-support.ts`, `http-test-support.ts`의 `positionalArgs`)로만 남겼고 운영 코드는 가져오지 않는다. 그것을 쓰는 시험이 없어지면 덮개를 지운다.

미룬 것: `postgres/`·`showcase/` 서비스 39개 파일에 되풀이되는 `BEGIN`/`COMMIT`/`ROLLBACK` 묶음을 `withTransaction` 도우미 하나로 모으는 일은 하지 않았다. 서비스 39개 파일을 건드리는 큰 변경이라 동작을 바꾸지 않는 이번 구조 정리와 따로 하고, 거래 경계가 같은지 서비스별로 확인하면서 옮긴다.

근거: 인라인 동등성 비교(`89d7a5e4` 대비 1797/1797줄, 차이는 로그아웃 블록 위치뿐), API 단위 597/597, PostgreSQL 524 pass / 0 fail / 3 skip, 교차 리뷰(Claude Sonnet·Claude Opus) 승인([TEST_STATUS](TEST_STATUS.md)).

## D-089 NFT 발행 Worker 상시 실행 (PR #420, 2026-10-08)

처음에는 D-080으로 적었으나 main의 D-080(실사용 전환 범위)과 번호가 겹쳐 D-089로 바꿨다(D-088은 main의 API 서버 구조 규칙으로 PR #422에서 병합됐다). 이미 푸시된 커밋 메시지의 "D-080"은 이력이라 고치지 않는다.

**상세 결정·구현 기본값:** **소유자 지시(2026-10-08):** Worker를 상시 동작으로 바꾸려는 설계 추천(단발 `start:once` 주기 실행, 전용 상시 루프 컨테이너, API 안 루프 비교)을 받은 뒤 "B안대로 구현"을 지시했다(전용 상시 루프 컨테이너). 독립 리뷰(Sonnet·Opus)의 지적을 고치고 병합하라는 지시도 받았다. **구현 선택(`PROPOSED`, 에이전트):** (1) 한 프로세스가 설정·keystore 복호화·DB 풀·게이트웨이를 한 번만 만들고 반복한다(작업이 있으면 200ms 쉼만 두고 이어서, 없으면 3초+지터, 예외는 1초에서 30초까지 두 배씩). (2) `SIGTERM`은 처리 중인 한 건을 끝낸 뒤 종료 코드 0, 설정 오류는 반복하지 않고 종료 코드 1. (3) 반복마다 기록된 커서에서 이벤트 조회 시작 블록을 다시 계산한다(안 하면 오래 뜬 프로세스의 조회 범위가 계속 늘어남). (4) 프로세스는 1개(체인당 서비스 민터 하나). 둘을 띄워도 같은 `DATABASE_URL`이면 어드바이저리 락으로 안전하고 임대 소유자는 `WORKER_ID`에 호스트 이름·pid를 붙여 프로세스마다 다르다. (5) 하트비트 파일과 컨테이너 헬스체크. 이 신호는 루프가 살아 있다는 뜻이지 발행이 성공한다는 뜻이 아니며 실제 신호는 대기열 길이다. (6) 운영 compose의 `mint-worker`는 프로파일 `nft-live`로만 켜지고 평소 배포·배포 스크립트에는 나타나지 않는다. 운영 API의 `NFT_MINTING_MODE: PREPARING`은 그대로다. (7) 민터 keystore·비밀번호는 저장소·이미지 밖 호스트 폴더를 읽기 전용으로 bind하고 폴더가 없으면 만들지 않고 거절한다. (8) Dockerfile은 Worker의 저장소 루트 판정 때문에 `/app/apps/worker`에 둔다. (9) 영수증 대기는 ethers 6.17의 `waitForTransaction`을 쓰지 않고 `getTransactionReceipt`·`getBlockNumber`를 2초 간격으로 30초까지 부르는 유한 조회로 직접 하고, RPC 요청 하나는 10초에서 끊는다(ethers 기본 300초면 응답 없는 RPC가 `confirmMint`를 약 10분 붙든다). 최악의 경우 한 번의 확인은 약 50초(기한 30초 + 마지막 요청 2건 × 10초)다. 그 함수는 조회 오류를 RPC 주소(API 키 포함)째 `console.log`하고, 비동기 실행기 안에서 던져 처리되지 않은 거절로 프로세스를 죽이며, 시간 초과 뒤에도 리스너를 남긴다. 조회 오류는 버리고 코드만 내며 기한이 지나면 조회가 멈춘다. 코드는 마지막 조회가 정한다: 마지막 조회가 오류였으면 `RECEIPT_LOOKUP_FAILED`, 깨끗했지만 영수증이나 확인 깊이가 아직 없으면 `RECEIPT_NOT_READY`(원래 코드로 되돌림). 둘 다 같은 재시도 경로이고 코드는 기록만 된다. (10) 잡히지 않은 예외·거절은 `MINT_WORKER_CRASHED` 한 줄(오류 이름·코드만) 뒤 종료 코드 1로 끝내고, DB 연결의 오류는 유휴 연결이든 처리 중에 빌려 간 연결이든(풀은 빌려 줄 때 자기 리스너를 뗀다) `MINT_WORKER_DB_POOL_ERROR` 한 줄만 남기고(같은 오류가 풀과 연결 양쪽으로 와도 한 줄) 넘어가 다음 질의가 정상 경로로 실패해 물러나게 한다. (11) 컨테이너의 `CHAIN_FROM_BLOCK`은 기본값 없이 환경 파일에서만 받고(계약 배포 블록), 비어 있으면 Worker가 시작을 거절한다. **하지 않은 것:** 운영 활성화, 운영 민터 키 생성(소유자만), 메인넷, 배포 스크립트·롤백 통합(켜기 전 후속: migrate 전 `mint-worker` 중지·배포 때 이미지 재빌드). 켜는 일은 [B-027](BLOCKERS.md) 전제와 `LIVE` 전환 승인이 먼저다.

**상태:** `USER_CONFIRMED`(구현 지시) · `PROPOSED`(세부 값)

**근거·영향:** [PR #420](https://github.com/2026-KW-HACKATHON/27_MassCOM/pull/420), 브랜치 `feat/worker-continuous-loop`(기준 main `e06c97cd`), [Worker README](../apps/worker/README.md)의 "상시 실행(반복) 모드", [Lightsail README](../infra/lightsail/README.md)의 "NFT 발행 Worker", `tests/ops/compose_worker_profile_test.mjs`. **되돌리기:** 이 브랜치의 변경(`worker-loop.ts`·`run-worker-loop.ts`·게이트웨이 `setScanFromBlock`·`mint-worker` compose 서비스·Dockerfile)을 되돌리면 `start:once`만 남는다. 게이트웨이의 영수증 대기와 `close()`, 풀 오류 리스너, 임대 소유자 접미사는 `start:once`에도 적용되므로 되돌릴 때 함께 사라진다. 이 서비스는 아직 어디에도 배포·활성화하지 않았다(`NOT_RUN`).

## D-090 점진적 공개: 처음 온 사람은 첫 코인부터, 나머지는 필요할 때 (Issue #412, 2026-10-08)

**소유자 방향(2026-10-08, `USER_CONFIRMED`):** 처음 온 사람에게는 첫 코인부터 보이고 나머지 기능은 필요할 때 드러나게 한다. 친구·쪽지와 놀이는 새 사용자에게만 숨기고 사용자가 직접 켠다. **구현 선택(`PROPOSED`, 에이전트):** 입구만 단계에 따라 드러내는 점진적 공개를 앱에 넣었다.

단계는 셋이다. `first-coin`은 코인도 인정된 방문도 아직 없는 때, `after-first`는 코인이나 서버가 센 방문이 하나라도 있는 때(보상이 다음 방문에 오는 첫 방문도 포함), `regular`는 아래 중 하나라도 충족한 때다. 두 번째 가게, 인정된 방문 3회, 배지 3단계(방문 횟수에서 나오므로 따로 조회하지 않는다), 시연 보너스를 뺀 마일리지 200 이상(실버 뽑기를 살 수 있는 값), 쓰지 않은 만료 전 뽑기권이다. 열린 뽑기 풀만으로는 단계가 오르지 않는다(모든 계정에 같은 풀이 보이기 때문). 단계는 앞으로만 간다. 기기에 계정별로 `masscom.disclosure.v1:<계정>`을 저장하고 로그인·계정 전환 때 다른 계정 몫을 지우므로, 뽑기권을 쓰거나 환불해도 입구가 다시 사라지지 않는다.

가리는 것은 입구뿐이다. 경로(딥링크 포함)·데이터·잔액·서버 판정은 바뀌지 않고, 설정의 "더 즐기기"와 내 정보에서 모두 열 수 있다. 다섯 칸 탭(탐색·도감·홈·놀이·상점)은 그대로다. 첫 코인 전의 홈에는 마이룸·동행·코인 전시·상점 카드·머리글 마일리지 칩이 없고 방문 인증, "처음이라면 이 가게부터", 방문 목표가 중심이다. 첫 코인 뒤에는 마이룸·동행·코인 전시·머리글 마일리지 칩이 열리고, 마일리지로 뽑기를 살 수 있으면(가격은 서버 값) 상점 카드가 나오며, 도감에는 내 공간과 동네 놀이 안내가 열린다. 읽지 않은 우편이 있으면 우편 아이콘은 단계와 상관없이 보인다.

친구·쪽지(홈의 친구 단추, 가게 이웃 만나기, 우편 아이콘)와 놀이는 진행으로 자동으로 열리지 않는 사용자 선택이다. 선택은 기기에 저장하고 설정 "더 즐기기"에서 켜고 끈다(저장소를 읽기 전에는 스위치를 잠가 빈 기본값으로 덮어쓰지 않는다). 이미 친구가 있는 계정은 아직 고르지 않았다면 친구·쪽지가 켜진 것으로 보고, 친구를 추가하면 켠 것으로 기록한다. 사람이 고른 값은 늘 이긴다(끄면 친구가 있어도 꺼진다). 동네 놀이 안내는 첫 코인 뒤부터 보이고 누르면 켜진다.

요청 수: 탭 화면이 포커스를 받을 때는 머리글의 세 요청(친구·상점·우편)뿐이다. 단계를 가르는 답(`GET /collection`, `GET /coin-shop`)은 홈 자신의 조회와 방문 수령 성공 직후에만 읽는다(단골이면 읽지 않는다). 시연·QA 강제 스위치는 빌드 값 `EXPO_PUBLIC_DISCLOSURE=full`(CI는 비워 둔다)이다. 실행 중 훅 `setDisclosureOverride`는 이후 서버 시연 모드(T3/T4)용이며 아직 연결돼 있지 않다.

경계: 앱을 열고 저장소를 읽기 전 첫 한두 프레임은 `first-coin`으로 그려질 수 있다(읽고 나서 바로 바로잡힌다). API·DB는 바뀌지 않았다. 되돌릴 때는 앱 코드만 되돌리면 된다. 배포하지 않았다(소유자 결정 A). 실제 휴대전화 화면 확인은 `NOT_RUN`이다.

## D-091 시연 점주 "1인 2역": 계정에 묶인 메모리 속 넘김 (Issue #412, 2026-10-08)

**구현 선택(`PROPOSED`, 에이전트):** 시연에서 한 사람이 점주 화면과 손님 화면을 오가며 방문을 끝까지 해 볼 수 있도록, 서버가 방금 발급한 값을 두 화면 사이에서만 넘긴다. 두 종류다. `claim`은 점주가 발급한 방문 코드를 손님 방문 인증 화면이, `identity`는 손님의 2분 식별 QR을 점주 방문 확인 화면이 받는다.

D-065와의 대비: D-065는 점주 직원 화면에서 43자 고객 식별 토큰을 손으로 입력하는 대체 수단을 만들지 않는다고 정했다(비현실적이고 토큰 노출 위험). 이 결정은 그대로다. 이 넘김은 입력 수단이 아니라 앱 안 두 화면 사이의 전달이며, 시연 앱과 로컬 개발 빌드(웹은 scheme으로 같은 판정)에서만 단추가 나타난다. 운영 앱에는 단추도 넘김도 없다.

규칙: (1) 메모리에만 둔다. URL·로그·저장소·클립보드에 쓰지 않고 손으로 입력하지도 않는다. (2) 넘긴 계정에 묶인다. 다른 계정이 읽으려 하면 아무것도 받지 못하고 값이 지워진다(`notifications/pending-target.ts`와 같은 방식). (3) 한 번 읽으면 지운다. 같은 계정이어도 종류가 다르면 그 종류를 받을 화면을 위해 남겨 둔다. (4) 서버가 준 만료 시각이 지나면 버린다. 만료된 값은 어느 종류의 화면이 읽어도 버려진다(종류 확인보다 만료 확인이 먼저다). (5) 로그아웃·계정 전환·세션 무효화·체험 다시 시작에서 비운다(다른 계정이 이미 로그인한 뒤 도착한 옛 세션의 무효화는 현재 계정의 값을 지우지 않는다). (6) 서버가 계속 결정한다. 식별 확인·방문 코드 발급·수령 확정은 기존 단추로 눌러야 하고 서버가 점포 권한과 코드 상태를 다시 검사한다. 넘김 경로가 발급·수령을 대신 부르지 않는다.

화면 규칙: "손님 화면에서 받기"는 내 계정이 직접 만든 식별 QR로 시작한 방문에만 보인다. 다른 사람의 QR을 찍어 발급한 코드는 내 손님 화면이 받을 것이 아니다. 두 화면 모두 보관된 복구(`claim-pending`)를 읽고 확인하는 일이 끝난 뒤에 넘김을 받는다(복구 상태 `reading`→`found`→`settled`). 복구할 것이 있어도 넘어온 값을 버리지 않는다: 확인이 끝날 때까지 쥐고 있다가, 복구로 되살린 이전 발급 화면을 걷어 내고 새 값으로 시작한다. 점주 쪽 보관 기록은 이미 쓴 발급까지 48시간 동안 재생하므로, 점주가 코드를 손님 화면에 넘길 때 이 기기의 점주 쪽 기록을 지운다(이 기기의 손님 화면이 코드를 쥐기 때문이다). 지우지 않으면 시연 둘째 판부터 점주 화면이 열릴 때마다 지난 발급이 복구돼 새 식별 QR을 가렸다. 점주 화면의 단계 카드(① 열림, ② 손님 QR, ③ 방문 코드 발급, ④ 현황 확인)는 ①~③이 이 흐름의 라벨과 같은 시점에 켜진다. ④는 점주 화면이 열린 채 다른 기기의 손님이 확정하는 두 기기 흐름에서만 켜진다. 한 기기 1인 2역은 역할을 바꿀 때 점주 화면이 닫혔다 다시 열려 방문 확정 답을 쥐고 있지 않으므로 ④가 켜지지 않고, ④의 글("오늘·현황에서 확인")은 안내로만 남는다. 손님 화면의 "점주 화면에서 이 QR 확인해 보기"는 이 계정이 점주 체험 권한이 있는지 미리 알 수 없다(손님 쪽에는 그 답이 없고 요청을 늘리지 않으려고 새로 읽지 않는다). 대신 단추 위 한 줄로 권한이 있으면 점주 화면이, 없으면 권한 요청 화면이 열린다고 말한다.

한계: 값은 하나뿐이고(마지막 것이 앞의 것을 대신한다) 앱 프로세스가 끝나면 사라진다. 의도한 동작이다. API·DB는 바뀌지 않았다. 되돌릴 때는 `navigation/demo-handoff.ts`와 두 단추를 되돌리면 된다. 배포하지 않았다(소유자 결정 A). 실제 두 기기·한 기기 시연 확인은 `NOT_RUN`이다.

## D-092 점주 목적형 캠페인, 혜택 시간대 규칙, "첫 방문" 표기 정정 (Issue #412 트랙 T3 PR 1, 2026-10-08)

점주가 캠페인으로 풀 문제를 세 목적 중 하나로 고르게 하고, 한산한 시간대 캠페인의 시간대 조건을 서버가 판정하게 했다(`PROPOSED`, 소유자 2026-10-08 방향 4·10에 따른 에이전트 구현 선택). 이번 범위는 목적 모델과 시간대 판정, 표기 정정까지이고 혜택 쿠폰·비용 상한·결과 카드는 뒤따르는 PR이다. 소유자 결정 A에 따라 배포하지 않았다.

**목적과 조건.** `NEW_CUSTOMERS`(MassCOM에서 처음 확인되는 방문 늘리기), `REVISIT`(다시 방문하게 하기: 처음 방문한 날로부터 최소 N일 뒤부터 M일 안, 기본 1일·14일), `OFF_PEAK`(한산한 시간대 채우기)이다. 목적은 `campaign_purposes` 부속 표(migration `0068_campaign_purposes.sql`)에 캠페인당 한 행으로 두고 `campaigns`·`campaign_goals`는 건드리지 않는다. 목적 행이 없는 캠페인(기존 캠페인 전부)은 지금과 똑같이 동작한다. 관리자 초안 생성(`POST /api/web/admin/campaign-drafts`)이 선택 입력 `purpose`를 받아 캠페인·목표·목적을 한 거래로 만들고 감사 `CAMPAIGN_PURPOSE_SET`을 남긴다. 대표 메뉴는 그 점포의 메뉴가 있으면 그중 하나여야 한다. 목적에 맞지 않는 칸(예: 새 손님 목적에 시간대)은 조용히 버리지 않고 거절한다. 조건은 초안일 때만 만들거나 고칠 수 있고, 공개·중지·종료된 뒤에는 DB 트리거(`campaign_purposes_terms_guard`)가 거절한다. 예외는 점주가 확인한 소개 `intro_*` 세 칸(함께 있거나 함께 없음)뿐이다. 공개와 수정이 겹쳐도 트리거가 캠페인 행을 `FOR SHARE`로 잡아 공개 뒤로 수정이 새지 않는다.

**D1 시간대 규칙(소유자 방향 반영).** 시간대 밖에서 한 방문도 방문 인정은 그대로다. 방문·코인(진행)·보상권은 시간대와 무관하게 세고, 시간대는 혜택에만 쓴다. 기준 시각은 고객이 스캔한 시각(`visit_events.occurred_at`)이 아니라 코드를 만든 시각(`claim_slots.created_at`)이다. 다만 이는 코드 유효 시간(`ttlMs`, 15분) 안에 확정하거나 재발급할 때만이다: `확정(재발급) 시각 < created_at + ttlMs`이면 `created_at`으로, 그보다 늦으면(정확히 `created_at + ttlMs`부터) 확정(재발급) 시각으로 판정한다(`benefitJudgedAt`). 15분 유효 시간 안에 시간대가 끝나도 점원이 시간대 안에서 만든 코드면 대상이지만, 재발급은 만료 여부를 따지지 않아 며칠 뒤 다시 열린 코드가 처음 만든 시각의 시간대를 물려받으면 안 되기 때문이다. 재생(같은 코드를 다시 확정)은 처음 확정 때 저장된 `claim_slots.claimed_at`으로 같은 규칙을 적용해 재시도해도 같은 상태이다. 혜택 상태는 진행에 세어진 방문에서만 판정한다: 직원 본인 적립(`progressExcludedReason: STAFF_SELF`)과 같은 한국 날짜의 두 번째 방문처럼 `progressCounted`가 false인 방문은 시간대와 무관하게 `NONE`이다. 혜택 발급(PR 2)이 `benefit.state`에 기대므로 방문 인정 경로의 "세지 않는다"와 어긋나지 않게 한 것이다. 시간대는 한국 시간(서머타임 없음), 1~3개, 요일(ISO 1~7)과 `HH:MM`이며 시작 시각은 포함·끝 시각은 제외, 자정을 넘기는 시간대는 없다(둘로 나눈다). 끝 시각에만 `24:00`(그날 끝까지)을 허용한다. 이는 지시에 없던 확장이다: 없으면 자정까지 여는 시간대를 `23:59`로 적어야 하고 마지막 1분이 빠지기 때문이다. 관리자 양식은 끝 시각 `00:00`을 `24:00`으로 보낸다. 방문 인정 경로(방문 삽입, 진행 계산, `grantReachedGoals`, 잠금, 취소)는 바꾸지 않았다.

서버 응답은 필드만 더했다. `claim-slots` 발급·재발급 응답에 `windowStatus: IN_WINDOW | OUTSIDE_WINDOW | NONE`, `claim-slots/redeem` 응답(재생 포함)에 `benefit: { state: ELIGIBLE | OUTSIDE_WINDOW | NONE }`이다. `NONE`은 시간대 조건이 없다는 뜻이고(목적 행이 없는 옛 캠페인, 시간대가 없는 새 손님·재방문 목적) 진행에 세어지지 않은 방문(직원 본인, 같은 날 두 번째)에도 쓴다. `ELIGIBLE`은 세어진 방문이 시간대 안이라는 뜻이다. 신규·재방문 조건의 판정은 혜택 발급 단계가 따로 한다. 재발급은 유효 시간 안이면 처음 발급한 시각을 기준으로 해서 점원 화면의 안내가 복구 뒤에도 같고, 유효 시간이 지난 코드의 재발급은 요청 시각을 기준으로 한다. `windowStatus`는 새로 발급·재발급한 응답에만 있다: 이미 소비된 신원 토큰으로 같은 요청을 다시 보내 받는 재생 응답(앱의 200 `replayed`)과 점포 웹의 재생 응답(`replayed: true`)에는 없다. 클라이언트는 이 필드가 없을 수 있다고 본다. 기존 enum 값은 늘리지 않았다. 옛 앱은 모르는 필드를 무시하고, 새 앱의 해석기는 필드가 없거나 모르는 값이어도 방문 화면을 그대로 연다. 점원 화면(모바일·점포 웹)은 시간대 밖 코드에 "이 코드를 만든 시각은 캠페인 시간대 밖이에요(방문은 인정돼요)"(재발급 응답도 같은 규칙으로 판정한 결과를 그대로 보여 준다), 고객 방문 완료 카드는 진행에 세어진 방문이 시간대 밖이었을 때만 "이번 방문은 점주가 정한 캠페인 시간대 밖이었어요. 방문과 수집품은 그대로 인정돼요." 한 줄을 보인다(세지 않은 방문에는 붙이지 않아 "직원 본인…세지 않습니다"·"한 번만 셉니다" 줄과 어긋나지 않는다). 혜택은 PR 2에서 생기므로 이 문구들은 혜택을 말하지 않는다. 고객 가게 상세와 공개 가게 목록에는 선택 필드 `campaign.purpose`가 붙고(목적 없는 캠페인은 필드 없음) 상세 화면은 "이번 캠페인: 한산한 시간대 방문 · 평일 14:00–17:00"과 "점주가 정한 시간대 캠페인이에요…"처럼 점주가 정한 조건만 중립적으로 적고 혜택은 약속하지 않는다. **혜택(PR 2)이 생기기 전에는 목적형 캠페인을 공개하지 않는다.** 지금 공개하면 손님이 시간대 조건을 보지만 그 조건에 걸린 혜택은 없다. 점주가 `nextStepText`에 쓰는 글은 점주 책임이라 확인 대상이다.

**표기 정정(의도된 사양 변경).** 점주가 보는 "첫 방문/재방문"은 "이 가게에서 MassCOM이 처음 확인한 방문인가"일 뿐 평생 처음 온 손님이라는 뜻이 아니다. 그래서 점포 웹 카드는 "이번 주 처음 확인된 방문 / 다시 확인된 방문"(설명에 "새 손님이라는 뜻은 아니에요"), 모바일 가게 현황은 "이번 주 처음 확인된 방문"·"이번 주 다시 확인된 방문", 방문 CSV는 머리글 `방문구분(MassCOM 확인 기준)`에 값 `처음 확인된 방문`·`다시 확인된 방문`으로 바꿨다. API 필드 이름(`weekVisitors.first/repeat`)과 집계 정의는 그대로다. 점주 화면·CSV·안내 문서에 "신규 고객"·"첫 손님"을 쓰지 않는다는 것을 소스 시험(`tests/site/merchant-copy-no-newcomer.test.mjs`)으로 고정했다. 바뀐 기존 단언은 [TEST_STATUS](TEST_STATUS.md)에 적었다.

**미룬 것.** (1) 개인정보 처리방침과 첫 로그인 동의 문구는 방문 CSV 항목을 "가명 고객 표시·한국 날짜·첫 방문/재방문·보상 현황"으로 적고 있다. 처리방침 문구를 바꾸면 버전(`privacy-2026-10-07`)과 동의 재수집이 따라오므로 소유자 승인 없이 바꾸지 않았다(분류 설명으로는 여전히 맞다). 다만 실제 CSV(`merchant-operations.ts`)는 `방문일(KST)`·`방문시각(KST)`(초 단위)·`캠페인`·`방문구분(MassCOM 확인 기준)`·`수집보상 건수`·`쿠폰 발급 건수`·`쿠폰 사용 건수`이고 가명 고객 열은 없다. 방문 시각을 초까지 내보내는 것과 캠페인·쿠폰 건수가 방침에 적히지 않았고 라벨 문구도 방침과 다르다. 트랙 T6의 방침 버전 갱신 때 함께 바로잡는다([BLOCKERS](BLOCKERS.md) B-033). (2) `intro_*`의 쓰기 경로(점주 확인 참조 번호)는 파일럿 설정 패널 PR에서 만든다. 표와 트리거, CHECK는 이번에 만들었다. (3) 혜택·쿠폰·비용 상한, 결과 카드, 설문, 안내물은 뒤 PR이다. (4) `apps/production-web/server.mjs`의 `/merchants` 중계는 공개 소개 페이지용으로 이름·소개·주소·메뉴·영업시간만 골라 보내고 캠페인 필드를 아예 싣지 않으므로 바꾸지 않았다. 앱은 API를 직접 부른다.

**호환.** migration 0068은 새 표·함수·트리거와 감사 CHECK 확장(`CAMPAIGN_PURPOSE_SET` 하나, 기존 16개 전체 유지)뿐이라 `backward_compatible=yes`다. 이전 API 이미지로 되돌려도 새 표는 읽지 않을 뿐 기존 쓰기는 그대로 허용된다.

**배포 순서.** 새 API 이미지보다 migration 0068을 먼저 적용한다. 방문 발급·재발급·확정·재생 경로가 이제 `campaign_purposes`를 읽으므로(`LEFT JOIN`) 표가 없는 DB에서는 방문 확정이 실패한다. `scripts/deploy-lightsail.sh`는 `migrate`를 `api` 기동보다 먼저 돌리므로 그대로 따르면 되고, 수동 배포나 이미지만 바꾸는 롤아웃에서는 순서를 지킨다. 반대로 새 API를 되돌릴 때는 표가 남아 있어도 이전 이미지가 읽지 않으므로 문제가 없다(롤백 때 표를 지우지 않는다).

개인정보 안내는 CSV 실제 7열에 맞춰 코드상 `privacy-2026-10-09`로 갱신했다. 이 새 API·웹·모바일 소스는 아직 배포하지 않았다. 새 개인정보 버전 배포는 API·웹·운영/시연 APK·시연 웹 번들을 같은 릴리스로 제공하고 구/신 동의 조합을 검증하는 조건이다. 키 활성화만으로 이 새 버전이 배포된 것으로 기록하지 않는다.
## D-093 가게 사이를 잇는 코스와 서버 판정 장면 (Issue #412 T4 A, 2026-10-08)

소유자 방향 3번과 이번 구현 지시를 근거로 팀이 서로 다른 가게 2–4곳을 상황(AFTER_MEAL: 식사 후 들르기 좋은 곳, TAKEOUT: 포장해서 가져가기 좋은 곳, OTHER: 함께 들러볼 만한 곳)에 맞춰 코스로 구성한다. 단계마다 가게·방문 목표 1/3/5회·조각 이름·점주 참여 동의 기록 참조를 고정한다. 한 코스 안에서 조각 키는 고유하며 점주 참여 동의 참조는 단계마다 서로 달라야 한다. AI가 점포 이야기나 신규 고객 실적을 만들지 않는다. 같은 날 방문을 강요하지 않는다.

진행은 코스의 `[counts_from, ends_at)` 기간에 발생한 취소되지 않은 유효 방문(`visit_events`)을 가게별로 세어 판정한다. 게시할 때 `counts_from`은 기간 시작 이후로 고정되므로 게시 전 방문은 포함되지 않는다. 리롤은 단계 완료를 되돌리지 않는다. 방문 취소로 유효 방문 수가 목표 아래로 내려가면 단계는 미완료가 되고 이미 열린 장면은 STALE로 표시한다. 장면 열기는 서버가 한 트랜잭션에서 모든 단계를 다시 확인하며 계정·코스 advisory lock과 고유키로 중복을 막는다. 클라이언트 완료 주장값을 받지 않는다. 완성에 마일리지·쿠폰·새 코인을 지급하지 않는다.

초안 → 점검 → 게시 → 중지 순서다. 점검은 공개 운영 점포, 점주 확인 위치(OWNED), 가게 간 직선거리, 선택한 한국 시각의 영업시간, 업종 조합, 현재 공개 ACTIVE 캠페인의 목표·모집 여유를 확인하고 라벨이 있는 스냅샷으로 저장한다. 도보 제공자 호출을 재사용할 독립 함수가 없어 v1은 직선거리만 사용한다. 점검은 실시간 영업 또는 실제 도보 경로의 증명이 아니다. 게시에는 한 시간 이내 점검과 각 단계의 점주 참여 동의 참조가 필요하며 게시 순간에도 적격성을 다시 확인한다. 시연·게스트 체험 점포는 운영 게시 대상에서 제외한다. 게시 후에도 점포가 ACTIVE·공개 상태를 잃거나 현재 공개 ACTIVE 캠페인이 끝나거나 단계 목표를 제공하지 않으면 그 단계는 UNAVAILABLE로 표시하고 완료로 세지 않는다. 앱은 “지금은 이용할 수 없는 가게예요”라고 안내한다. 이용할 수 없는 단계가 하나라도 있으면 새 장면 열기는 불가능하되 이미 열린 기록은 유지한다. 2026-10-09 T9 리뷰 수정으로 앞선 v1 접근 제한을 변경한다. 코스가 PAUSED 또는 ENDED여도 취소되지 않은 `course_unlocks` 기록이 있는 계정은 `GET /me/courses/:id`와 목록에서 지난 코스·획득 장면을 읽을 수 있다. 다른 계정의 탐색·추천·조회에는 노출하지 않으며 새 장면 열기 POST는 계속 거절한다. 방문 취소·열기 기록 회수·계정 삭제의 기존 제한은 유지한다.

v1 장면은 팀이 정한 `scene_key` 이름과 각 가게에서 받은 코인 썸네일로 구성한다. 새 그림을 만들지 않는다. 추천은 진행 중인 코스의 다음 미완료 가게를 우선하며 기존 추천 reasonCode 세 값은 유지하고 선택 `course` 필드만 보탠다. 정원 마감 가게는 추천에서 제외하고 코스 상세에는 자리 없음을 표시한다. 조회는 도감처럼 선택 놀이 동의 없이 허용하며 장면 열기 POST는 현재 놀이 동의를 요구한다.

migration `0072_courses.sql`은 새 표 세 개·가드·감사 action을 더하는 추가 전용이다. `0068_campaign_purposes.sql`의 `CAMPAIGN_PURPOSE_SET`도 감사 CHECK 합집합에 보존한다. 운영 보상·수령·취소·0034 획득 트리거는 수정하지 않는다. 시연 코스 fixture는 시연 DB seed에서만 만든다. 계정 삭제와 삭제 계정 보존 정리는 코스 열기 기록도 제거하고 큐레이터 계정 ID를 가명 처리한다. 과거 API 이미지가 남긴 큐레이터 ID도 삭제 원장에 따라 제한된 배치로 재처리한다. 배포하지 않았다(소유자 결정 A). Studio 장면 배치는 후속 범위다.
**남은 위험(열림):** 상한이 없으므로 탈취된 민터 키는 계약이 일시 중지될 때까지 활성 시리즈에 잠긴 NFT를 제한 없이 발행할 수 있다. 총 NFT 가스 지출을 제한하는 장치는 민터 잔액 하한과 건당 수수료 상한뿐이다. 소유자가 상한 해제를 결정했지만 이 두 위험에 대한 별도 통제 결정은 없다.

## D-094 캠페인 혜택의 추가 원가 상한과 이미 발급한 약속 (Issue #412 T3 PR 2, 2026-10-09)

소유자 방향 4와 이번 작업 지시의 D·E를 구현했다. migration은 예약 번호 `0069_campaign_benefits.sql`만 쓰고, 다른 브랜치의 D-093·migration 0072는 바꾸지 않는다. 배포하지 않는다(소유자 결정 A).

- **상한의 뜻.** `issued_count`는 ISSUED+REDEEMED 행 수다. 만료된 미사용 쿠폰도 이미 발급한 것으로 남으며 상한을 자동 반환하지 않는다. `issued_count BETWEEN 0 AND max_uses` CHECK와 `status='ACTIVE' AND issued_count<max_uses` 조건부 증가가 신규 수령을 막는다. 상한 도달·발급 중지는 이미 발급한 쿠폰의 사용 가능 여부를 바꾸지 않는다. 비용·상한·내용은 수정할 수 없고, 상한을 바꾸려면 중지 후 새 혜택과 새 점주 동의가 필요하다. 관리자는 같은 점포 동의 다섯 항목과 정규화한 문서 참조 번호를 확인한다. 이전 PAUSED 혜택도 상태 목록에 남아 그 약속을 숨기지 않는다.
- **수령과 취소.** 방문 거래 안에서 발급하지 않는다. 고객이 별도 수령 경로를 호출하며 계정 수명주기 확인 뒤 고객·캠페인 advisory → 점포 FOR SHARE → 유효 원천 방문 FOR SHARE → 조건부 카운터 증가 → 쿠폰 삽입 순서를 쓴다. 같은 고객·캠페인의 재전송은 기존 쿠폰을 돌려준다. 방문 취소도 같은 advisory를 먼저 잡고 해당 방문의 미사용 쿠폰을 `VISIT_CANCELED`로 무효화해 `issued_count-1 WHERE issued_count>0`로 한도를 반환한다. 취소로 무효화한 행은 남기되 같은 고객의 새 유효 방문 수령을 허용한다. 사용한 쿠폰이 있으면 방문 취소를 거절한다.
- **목적과 시각.** MassCOM에서 점포의 처음 확인된 방문이 캠페인 기간 안인 경우, 첫 캠페인 방문 날짜 뒤 최소·최대 일수 안의 다른 날짜 방문, 또는 `claim_slots.created_at`이 KST 시간대 안인 방문을 각각 판정한다. 재방문 쿠폰의 `usable_from`은 조건을 채운 방문 날짜의 KST 자정+`revisit_min_days`다. 사용 시작 전에는 조회·사용을 막는다. 늦게 수령해도 DB 시간 CHECK를 깨지 않도록 유효 기간은 `max(수령 시각, usable_from)+valid_days`부터 계산한다. 방문 확정 `claim-slot-service.redeem()`은 바꾸지 않는다.
- **네 숫자와 원가.** 한 집계 질의로 발급(ISSUED+REDEEMED), 사용(REDEEMED), 아직 사용 가능(ISSUED이고 미만료), 만료 미사용, 추가 발급 가능량 `greatest(max_uses-issued_count,0)`을 읽는다. 추가 원가 부담=`사용×건당 추가 원가`, 최대 추가 원가=`상한×건당 추가 원가`, 이미 약속한 최대 비용=`(사용+미만료 ISSUED)×건당 추가 원가`다. 원화 곱셈은 bigint이고 JSON에는 십진 문자열로 보낸다. 미래 사용 시작 쿠폰도 미만료 약속에 포함한다. 관리자·점주 화면은 이를 추가 원가로 표시하며 매출·이익 성과로 바꾸지 않는다.
- **고객·삭제.** 고객 응답에는 비용·상한·재고 숫자를 넣지 않고 가능 여부는 "받을 수 있음"/"모두 소진"만 표시한다. 기존 쿠폰 모양에 선택 `usableFrom`을 더해 직원 조회·사용과 고객 QR을 재사용한다. 계정 삭제는 고객·사용 처리자·무효 처리자를 가명화하며 행과 비용 약속을 삭제하지 않는다. 사용 되돌리기는 10분 안에만 허용한다. 지정 스키마에는 사용 되돌리기 감사/재생 표가 없어 두 번째 되돌리기는 `COUPON_NOT_REDEEMED`다(별도 재생 원장 확장은 후속).

실행 증거와 한계는 [TEST_STATUS](TEST_STATUS.md) 맨 위와 [HANDOFF](HANDOFF.md)에 기록한다. 운영·시연은 공통 고객 코드지만 실제 두 variant 설치·기기 수용은 각각 NOT_RUN이다.

## D-095 NFT 시리즈 발행 수량 상한 해제 (2026-10-08)

**소유자 결정(`USER_CONFIRMED`, 2026-10-08):** 오프라인 회의에서 NFT 수량 제한을 해제하기로 합의했다. 코드는 상한을 보존하지 않고 고치기로 소유자가 정했다. 이 결정은 D-023의 "비용 상한은 쿠폰·NFT 시리즈 상한" 중 NFT 시리즈 상한을 없애며, 쿠폰 발급 상한과 배지 상자 혜택의 `issuance_cap`은 그대로다. 상한을 대신하는 비용 통제 장치는 정하지 않았다. Worker가 내는 발행 가스비는 이제 발행 건수에 비례해 늘 수 있다.

**구현 선택(`PROPOSED`, 에이전트):**
- 컨트랙트: `createSeries(seriesId, baseTokenURI)`로 인자를 줄이고 `SeriesSupplyExceeded`·`InvalidSeriesSupply` 오류와 `SeriesCreated`의 `maxEverMinted`를 없앴다. 시리즈 존재 여부는 비어 있지 않은 `baseTokenURI`로 판단한다. `everMinted`는 세기만 하고 제한하지 않는다. `series(bytes32)` getter가 `(string,uint64,bool)`로 바뀐다.
- API: 발행 신청에서 시리즈 수량 검사와 `CAPACITY_UNAVAILABLE`을 없앴다. 중복 발행은 보상권 1회·`reward_key`·멱등 키로만 막는다. 앱의 해당 오류 문구도 뺐다.
- DB: migration 0075이 `nft_series.max_ever_minted`의 NOT NULL만 푼다. 새 API는 이 열을 읽지 않아 옛 스키마에서도 동작한다. 배포된 옛 API를 위해 열은 남기지만, 옛 API는 NULL 상한 행을 `CAPACITY_UNAVAILABLE`로 거절한다. 따라서 모든 API 인스턴스가 새 버전이 된 뒤에만 NULL 상한 시리즈를 삽입한다. 옛 API로 롤백하려면 원래 `integer`인 열을 `numeric(20,0)`으로 넓히고 NULL 행의 `max_ever_minted`를 uint64 최댓값 `18446744073709551615`로 채운 뒤 `SET NOT NULL` 한다. 열 삭제는 별도 migration으로 한다. 운영·시연 DB에는 현재 `nft_series` 행이 없다.

**경계와 한계:** 이미 Base Sepolia에 배포된 컨트랙트(`docs/evidence/base-sepolia-deployment.json`, 상한 1)는 바뀌지 않는다. **기존 상한 1 실증 시리즈에는 운영 발행을 보내지 않는다.** 기존 계약에서 새 시리즈를 만들 때는 실제 배포된 시그니처 `createSeries(bytes32 seriesId, string baseTokenURI, uint64 maxEverMinted)`의 세 번째 인자에 `18446744073709551615`(uint64 최댓값)를 넣어 사실상 상한 없이 운영한다. 새 계약에서는 2인자 `createSeries(bytes32 seriesId, string baseTokenURI)`를 쓴다. Worker 운영 코드는 `createSeries`를 부르지 않는다. 기존 계약에서 `SeriesSupplyExceeded`가 발생하면 제출 전 gas 추정에서 이 오류가 확인되면 Worker는 재시도하지 않고 `SERIES_SUPPLY_EXCEEDED`로 즉시 `MANUAL_REVIEW`에 보낸다(추정 뒤 경합으로 채굴된 revert는 기존 `MINT_TRANSACTION_REVERTED` 재확인 경로를 따른다)(권리는 `MINT_REQUESTED`로 남아 운영자 복구 판단 필요). 배포된 컨트랙트의 기존 시리즈 상한은 바꿀 수 없다. PRD RQ-014(공급 상한)는 이 결정으로 더 이상 요구가 아니다.

**남은 위험(열림):** 상한이 없으므로 탈취된 민터 키는 계약이 일시 중지될 때까지 활성 시리즈에 잠긴 NFT를 제한 없이 발행할 수 있다. 총 NFT 가스 지출을 제한하는 장치는 민터 잔액 하한과 건당 수수료 상한뿐이다. 소유자가 상한 해제를 결정했지만 이 두 위험에 대한 별도 통제 결정은 없다.

## D-096 점주 방문 보상 고정과 회전 깊이 저장 (PR #418, 2026-10-08)

**소유자 직접 결정(USER_CONFIRMED):** 메뉴 등록을 요구하지 않고 단계별로 진행하며, 1·3·5회 캠페인은 점주가 제어할 수 없게 한다. 음각·양각이 회전할 때 깊이가 보이는지, 애니메이션과 저장 형식도 확인한다.

**구현 선택(PROPOSED, 에이전트):** 지급은 1회 브론즈·3회 실버·5회 골드로 자동 연결한다. 정확한 1/3/5 활성 캠페인이 없으면 초안 저장은 가능하고 게시를 막는다. 서버가 입력 매핑도 고정하고 점주 연장 HTTP 경로와 서비스 권한을 차단한다. 관리자 연장은 유지한다. 음각·양각은 원본 밝기×alpha 높이에서 반대 부호의 조명·변위를 계산하는 2.5D로 만든다. 원본과 편집 이력은 초안 JSON에, 완성품은 기존 12칸·4열·15° 앞면 스프라이트와 고정 뒷면·모션 JSON에 저장한다. 최신 소유자 요청에 따라 프리즘을 포함한 네 기본 등급과 활성 특수등급까지 모두 게시한다(최신 후속 D-097). 형식 변경과 GIF/동영상만 저장하는 안은 기존 앱 호환과 각도 조작·편집 보존을 위해 채택하지 않았다.

## D-102 회전·움직임 분리와 런타임 오라/옆면 (새 PR, 2026-10-09)

Flame 같은 이글거리는 효과는 움직임·재질과 함께 보되 새 **오라** 항목으로 둔다. 재질 효과 강도는 실제로 보여야 하며, 미리보기는 재생/정지 한 버튼으로 전환한다. 표현 스타일은 애니메이션보다 위에 둔다. 회전과 움직임은 서로 따로 있어야 한다. 코인 후면도 정면처럼 회전 실시간 조명·반짝임이 보여야 하며, 옆면 테두리는 실제 동전 같은 고정 무늬를 쓰되 얇은 코인에서도 괜찮아야 한다.

**구현 선택(PROPOSED, 에이전트):** 3단계는 표현 스타일(원본·흑백·음각·양각) 다음에 애니메이션과 효과를 둔다. 애니메이션과 효과 안에서는 `회전` 탭을 기본으로 열고 `움직임`, `재질 효과`, `오라`, `목소리`, `살아 있는 그림`, `가게 이야기`를 별도 탭으로 둔다. 회전은 `rotationSpeed`와 수동 각도, 움직임은 기존 once/loop motion JSON을 담당한다. 2단계는 새 사용자에게 기본 스티커를 자동 삽입하지 않고, 새 점포 추천 motif·메뉴 문구도 스티커로 만들지 않는다. 저장된 사용자 스티커는 계속 보존한다. 오라는 `flame` 효과의 색·강도·속도만 저장하고 별도 이미지 타일을 만들지 않는다. 재질 강도0은 no-op이다. 후면12종은 기존 고정 이미지를 재사용하며 회전 각도별 조명·프리즘 glint를 런타임에서 다시 합성한다. 프리즘이 아닌 테두리도 `baseColor` 단색 대신 현재 등급 금속색 gradient를 쓰게 하여 실버 림이 브론즈색처럼 보이는 문제를 막는다. 옆면은 모양별 144칸 reeded edge를 고정 규칙으로 만들고, 투영 간격이 2px보다 작거나 얇은 두께에서 과밀해지는 홈은 줄이거나 생략한다. 앞면/후면 이미지를 새로 대량 저장하는 대신 기존 스프라이트·고정 뒷면·metadata 저장 형식을 유지한다. 실제 재생은 웹·앱75ms/도×배율로 맞추며 모든 움직임과 함께 회전한다. 재생 버퍼256px·정지/내보내기512px, 프리즘 픽셀 계산 공유와 연속 측면 경로로 비용을 줄인다. [캡처·게시·성능](evidence/coin-edge-2026-10-09/README.md)을 검수했다. 최악 각도 계산의50ms 초과는 남아 있고 Android 실기·운영 배포는 별도다.

## D-103 앱 시작부터 배경음 재생 (소유자 직접 요청, 2026-10-09)

**소유자 결정(`USER_CONFIRMED`):** "음악이 처음엔 안 나오고 뽑기 한 후부터 재생됨" 보고에 따라 배경음은 뽑기 화면 첫 방문과 관계없이 앱 전체에서 재생한다. 이 결정은 D-084의 "배경음 플레이어는 첫 뽑기 화면 초점에서 만든다"는 선택을 대체한다. D-075의 뽑기 초점 intro→loop와 이탈 loop, 켜기/끄기·음량·진동·저장 설정은 유지한다.

**구현:** 네이티브는 루트 첫 렌더 뒤 지연 타이머, 웹은 기존 UI 소리의 첫 `pointerdown`·`keydown`·`touchstart` 경로에서 음악을 활성화한다. 설정 hydrate·BGM 켜짐·전경·backend 준비 조건에서 플레이어를 만들고 loop를 시작한다. 큰 MP3의 플레이어 지연 생성과 기존 자산 경로를 유지한다. 웹 autoplay 거절은 버전 고정 expo-audio 패치에서 promise를 처리하고 재생 상태를 정리하며 UI를 중단하지 않는다.

공통 코드가 운영·시연 variant와 Expo 웹에 적용된다. 자동 시험과 한계는 [TEST_STATUS](TEST_STATUS.md)의 앱 시작 배경음 절을 따른다. 실제 브라우저 autoplay/청음·각 Android variant 실기·첫 화면 성능·배포는 NOT_RUN이다. 되돌리기는 이번 공통 컨트롤러·입력 이벤트·expo-audio 패치를 되돌리며, 저장 설정 형식과 API/DB는 그대로다.
