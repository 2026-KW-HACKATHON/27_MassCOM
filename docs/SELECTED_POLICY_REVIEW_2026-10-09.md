# P4·X2 정책 및 구현 경계 검토

기준: 2026-10-09 KST, PR #435 `644beb75` 위 후속 작업. 아래 경로는 저장소 기준이다. 현재 구현 상태와 이번 사용자 확정 전제, 미승인 제안을 구분한다.

## 확정 범위

음식점별 보상은 해당 이용자가 함께 사용하는 단일 공유 풀이라는 사용자 전제를 따른다. 개인 풀이나 새로운 분리 체계를 만들지 않는다. 이번 작업은 비복원 추첨·7일 자동 사용·쿠폰 정책 변경을 선택하지 않았다. NFT, 보유품, 방문, 기발급 보상권·쿠폰은 보존한다. 과거 BASE/PRISM 양자택일·기간 문구는 기존 코드의 설명이며 새 정책의 승인 근거가 아니다.

## P4: 잔여 수량 기반 프리즘 표시 — BLOCKED

현재 코드는 P4에 필요한 실제 잔여 수량을 제공하지 않는다.

| 근거 | 확인 결과 |
| --- | --- |
| `apps/api/migrations/0059_coin_economy.sql:4–28` | 가게 연결 풀 항목에 `weight`만 있고 잔여 수량은 없다. 개인 풀은 아니지만 가게당 한 풀을 강제하는 제약도 없다. 이는 현황이며 새 풀 정책이 아니다. |
| `apps/api/src/postgres/coin-economy.ts:130–142` | 확률은 고정 `weight / total`이다. |
| 같은 파일 `480–510` | `issued_count`는 티켓 발급 수다. 발급 상한과의 차이를 코인 재고로 해석할 수 없다. |
| 같은 파일 `518–551` | 사용은 고정 가중치 추첨 결과를 저장하며 항목 재고를 차감하지 않는다. |
| migration0059 `107–121` | 항목 수정·삭제 방지 트리거가 있다. 잔여 재고 도입에는 별도 데이터·추첨 변경이 필요하다. |

P2·P3 전체 명세가 이번 요청에 없어 ID별 완료 판정은 하지 않는다. 다만 P4가 요구하는 잔여 수량 저장·조회·차감 근거가 현재 코드에 없어 선행 조건 충족으로 볼 수 없다. 해당 구현을 이번 변경에 임의로 포함하지 않는다. **탐색 배지·임계값·확률 상승 문구를 추가하지 않았다.**

### 기존 상세 확률 노출의 별도 위험

`routes/coins-rooms.ts:51–60`과 `postgres/coin-economy.ts:281–303`의 `/coin-shop`은 인증·동의만 확인하고 판매 풀 상세 `entries`를 반환한다. 따라서 기존 API는 비보유자에게도 고정 확률을 제공한다. P4 탐색 화면에 이를 재사용하지 않으며, 기존 노출 제한까지 완료했다고 주장하지 않는다. 화면만 숨기면 응답으로 확률을 복원할 수 있다.

### 구현 전에 결정할 내용 — 모두 미승인

- 보유자 정의: 해당 가게 코인, 해당 풀의 미사용 티켓, 둘 중 하나 여부.
- 표시 기준: 절대 확률, 최초 대비 상승폭, 비교 가능한 가게 사이 상대 기준 중 선택. 임계값·문구·갱신 주기도 미정이다.
- 기존 복수 풀 데이터와 사용자 단일 공유 풀 전제의 이행 방법. 새 개인 풀/분리 체계로 해결하지 않는다.
- 잔여 재고 구현 후 분모는 승인된 동일 공유 풀의 추첨 대상 잔여 수량이어야 한다. 강화권·등급 필터는 별도 규칙이 필요하다.
- 전체 재고 0·조회 실패·오래된 값일 때 확률을 추정하지 않는 표현.

권장 순서(제안): P2/P3 실제 데이터·추첨 근거 확인 → 보유자/서버 노출 범위 확정 → 표시 기준 확정 → P4 화면 적용.

수용 시험: 다른 이용자의 추첨 후 공유 잔여값 동기화, 동시 추첨 음수 재고/초과 지급 방지, 프리즘0·전체0·통신 실패 처리, 비보유자 응답에서 상세 확률/가중치/복원 가능한 상세 재고 제거, 계정 전환 캐시 격리, 배지와 접근성 문구 일치.

## X2: 인정된 동일 방문의 동행 보상 — 정책 분석 완료, 지급 구현 보류

### 재사용 가능한 개인별 인정 방문 증거

| 근거 | 기존 보장 |

`apps/api/migrations/0003_claim_slots.sql:16–18`의 고유 키는 가게·고객·주문참조 해시다. 동일 주문에서도 고객마다 별도의 슬롯을 받는 기반은 있다. `apps/api/src/group-claim.postgres.integration.ts:53–105,122–147`에는 3명 개별 슬롯, 타인 토큰 거절, 동시 재시도 신규1회, 미수령자 방문/보상0 시험이 있다. **시험 코드 확인이며 이번 DB 실행 결과는 아니다.**

### 없는 증거와 악용 위험

`migrations/0050_social_mail.sql:72–97` 및 `postgres/social.ts:504–552`의 식사 초대는 예정 시간·수락만 저장하고 인정 방문과 연결하지 않는다. 초대 수락, QR 링크 보유, 동일 가게·날짜만으로 실제 동행을 증명할 수 없다. 기존 NORMAL/SILVER 재뽑기권은 관리자 지급·기존 코인 소모·등급 제한 규칙이 있는 다른 권리다(`postgres/coin-economy.ts:312–326,395–427`). 이를 동행 희귀도 강화권으로 전용하지 않는다.

### 선택 가능한 인증 정책안 — 미승인

| 안 | 이점 | 한계/추가 결정 |
| --- | --- | --- |
| 동일 주문 참조에 묶인 개인별 인정 방문 | 기존 슬롯 재사용, 작은 구현 범위 | 분할 결제 누락 가능, 주문 일치만으로 실제 동석 보장 불가 |
| 점주 확인 동행 세션과 개인별 인정 방문 연결 | 분할 결제·참가자 확정 표현 가능 | 세션 수명·마감·정정·추가 UI 정책 필요 |

어느 안도 채택·구현하지 않는다. 공통 조건은 각 참가자의 인증 계정, 유효한 인정 방문, 서버에서 검증한 동일 방문 연결, 참가자별 지급 멱등성이다.

### 강화권 지급 전 필요한 결정 — 미승인

인원·마감·친구 여부·일일 상한, 지급 시점, 방문 취소 시 미사용 권리 처리, 강화 방식(후보 제한/재가중), 적용 대상·중첩·만료를 확정해야 한다. 강화는 같은 공유 풀의 희귀 재고 소진을 앞당겨 다른 이용자에게 영향을 줄 수 있다. 이미 사용한 권리·확정 코인·NFT·기발급 쿠폰을 별도 결정 없이 회수하지 않는다. 토큰 재사용 방지만으로 다계정·점주 공모까지 방지했다고 볼 수 없다.

### 구현 재개 시 수용 기준

1. 초대만 수락한 참가자는 지급0.
2. 타인·만료·폐기·재발급 전 QR 사용 불가.
3. 동일 슬롯 재시도·동시 요청·다른 요청 ID에도 참가자별 최대1회 지급.
4. 여러 초대에 연결된 같은 계정/여러 사람이 공유한 한 QR로 추가 지급 불가.
5. 같은 가게의 별도 식사·다른 날짜·다른 주문을 동행으로 오인하지 않음.
6. 기존 인정 방문 제외 조건·취소를 동일하게 적용.
7. 방문 취소와 지급의 경쟁을 원자 처리. `postgres/reversal.ts:149–168`의 잠금 순서 보존.
8. 강화권 도입 시 동일 공유 풀 재고 보존, 확률 합계, 재시도 결과 고정 검증.
9. 기존 NFT·보유품·쿠폰·방문 이력에 불필요한 변경 없음.

## 검증 한계

API·스키마·시험 코드 정적 확인만 수행했다. 이번 P4/X2 검토로 DB 통합 시험, 운영 보안 수용, 실제 동행 확인이 완료된 것은 아니다. 정책 미확정으로 P4 표시 및 X2 지급 코드·마이그레이션은 추가하지 않았다.
