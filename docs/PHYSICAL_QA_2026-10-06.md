# 2026-10-06 Android 실기 검증 중간 결과

사용자가 연결한 Samsung SM-S928N(Android 16, API 36)에서 개발 앱을 실행했다. **재연결 후 사용자가 소리 들림을 확인했고, 진동 체감은 아직 FAIL이다. 전체 실기 검증은 완료되지 않았다.** 에뮬레이터로 결과를 대신하지 않았다. 아래 초기 결과는 당시의 상태이며 최신 재연결 결과가 우선한다.

## 재연결 후 최신 결과

- 앱 설정은 실제 UI에서 효과음·BGM ON/각각 30%, 진동 `전체`로 확인했다. 휴대폰은 사용자가 `NORMAL` 벨소리 모드·스피커 미디어 9/15로 바꾼 상태였으며 에이전트는 벨소리·미디어 음량을 변경하지 않았다.
- 개발 검증 서버의 두 환경 문제를 찾았다. 다른 체크아웃에 연결한 `node_modules`와 개발 lazy bundle 때문에 `expo-audio/build/index`와 `expo-haptics/src/Haptics` 로드가 실패했고, Expo 57의 개발 `expo/virtual/env`는 `.env.local`을 shell 값 위에 합쳐 `EXPO_NO_DOTENV=1`만으로 주입 QA 환경이 보장되지 않았다. 임시 개발 로그로 두 패키지 로드 실패를 확인한 뒤 로그는 제거했다. 실제 개인 환경 파일의 값은 읽거나 수정하지 않았다.
- 검증 서버는 **개발 패키지 + release 방식 JavaScript 변환**(`--dev-client --no-dev`, `EXPO_NO_METRO_LAZY=1`, `EXPO_NO_DOTENV=1`)으로 바꿨다. 전체 SDK를 JS 번들에 포함하고 개발 virtual-env 파일 합침을 제외했다. 번들의 QA 계정과 loopback API, virtual-env 합침 부재를 확인하고 합성 계정의 홈으로 돌아왔다. 오디오·진동 제품 코드는 이 환경 교정 때문에 바꾸지 않았다.
- **PASS — 사용자 청음:** 실버 구매 뒤 앱을 전면으로 복귀시킨 상태에서 사용자가 “오 소리 들림”이라고 확인했다. 음악·각 효과음을 따로 구별한 청음이나 진동/무음 모드에서의 최종 수용 결과는 아직 주장하지 않는다. 다른 앱으로 전환하면 기존 전경 정책에 따라 음악이 일시정지됐다.
- **FAIL — 사용자 진동 체감:** 같은 실버 연출에서 해당 개발 앱의 진동 5회가 Android에서 `finished`, 50ms/진폭 약 0.12로 기록됐지만 사용자는 진동이 느껴지지 않는다고 했다. 표준 Android shell 150ms/default amplitude 비교도 `finished`(약 190ms)였고 사용자는 미체감으로 답했다. 이것만으로 앱의 약한 파형이나 기기 고장을 확정하지 않는다. 손에 든 준비 상태의 연속 진동 비교 응답을 기다린다. 시스템 진동 강도·DND를 강제로 바꾸지 않았다.
- **PASS — 홈 초기 개선 실기:** 수치·QR·미션 진입을 상단에 모으고 두 가게권 미리보기와 제목 옆 전체 보기/접기를 확인했다. 200% 글자에서는 헤더·요약·QR·미션·전체 보기 버튼의 겹침을 관찰하지 않았다. 긴 가게권 본문 200%는 아직 미검증이며 글자 크기는 1.0으로 복원했다. 이후 사용자 제안대로 요약 홈과 가게권·미션·전시 상세로 나눴다. 기본 글씨의 요약 홈과 세 상세/뒤로, 200% 홈 스크롤·전시를 실제 폰에서 확인했다. [최신 홈 QA](HOME_OVERVIEW_QA_2026-10-06.md)가 분리 이후의 근거다.

실폰을 사용자가 함께 조작하므로 앱이 다른 화면으로 전환될 수 있다. 화면 증거는 개발 앱의 전면 상태를 확인하고 합성 데이터 화면만 보관한다. 진단용 전체 시스템 로그와 다른 앱 화면은 공개 증거로 올리지 않는다.

## 환경과 증거 범위

- 화면: 720×1560, density 300, 원래 글자 배율 1.0. 접근성 시험 때 글자 2.0을 임시 적용하고 1.0 복원을 확인했다. 테마·벨소리·미디어 음량은 에이전트가 바꾸지 않았다.
- 설치 패키지: `kr.masscom.wolgye.dev`, versionName `0.1.0-test.2`, versionCode 2. 기존 개발 앱에 `adb install -r`가 성공했다. 데이터 초기화나 운영·시연 앱 교체는 하지 않았다.
- 설치한 APK SHA-256: `7d64c700227dd99eb32af021f22d4b779f439d84c3461fb758c7d398ad76f339`. 이는 APK 파일 해시이며 Git 커밋이 아니다. 실제 APK의 `ExpoModulesPackageList`에 `AudioModule`과 `HapticsModule` 등록, VIBRATE 권한을 확인했다.
- 아래 화면은 병합 main `3606183826d4b95944c4436a57143bafdcb29f09`의 JavaScript를 Metro로 제공한 개발 클라이언트 결과다. 공개 APK에 이 커밋이 내장됐다는 증거가 아니다.
- 계정·점포·방문·마일리지는 격리된 로컬 QA DB의 합성 데이터다. 개발 모드의 주입 계정만 사용해 기존 실제 로그인 세션을 복원하거나 전송하지 않았다. 실제 Google 로그인·FCM 수신·운영 데이터는 시험하지 않았다.

## 확인한 원인과 수정

실기 오디오 상태는 벨소리 `VIBRATE`, 방해금지 OFF였다. 현재 공통 오디오 정책의 `playsInSilentMode: false`와 설치된 `expo-audio 57.0.5`의 Android 구현은 진동·무음 모드에서 `play()`를 반환한다. 같은 동작은 [Expo SDK 57 문서](https://docs.expo.dev/versions/v57.0.0/sdk/audio/#audiomode)에도 명시돼 있다. 따라서 해당 모드는 재생을 막는 확인된 조건이다. 앱 설정과 실제 재생 상태를 읽지 못했으므로 모든 미체감을 이 조건 하나로 확정하지 않는다. 진동 미체감의 원인도 아직 확정하지 않았다.

[Issue #376](https://github.com/2026-KW-HACKATHON/27_MassCOM/issues/376)의 별도 재현에서는 인트로·반복 플레이어가 처음에 미로드이면 음악 재생을 건너뛴 뒤 로드 완료에도 재시도하지 않았다. 공통 `ui-sound-controller.ts`에서 현재 대기 음악만 로드 이벤트 후 재개하도록 수정했다. 중복 이벤트, 화면 이탈 뒤 인트로, 음소거·백그라운드·해제 뒤 오래된 이벤트는 차단한다. 반복 음악이 로드 중일 때 기존 인트로를 멈춰 화면 의도와 맞췄다. 진동 코드·음소거 정책·오디오 권한·보상·인증·의존성은 보존했다.

수정 전 지연 인트로·지연 반복·화면 이탈 시험의 기대 재생 횟수가 0으로 실패했고, 수정 후 컨트롤러 18/18과 전체 모바일 1,678/1,678, 타입 검사·린트·diff 검사가 통과했다. 독립 검토는 P1/P2 차단 결함 0건, 컨트롤러 18개·추가 경쟁 조건 4개 PASS, 두 파일 TypeScript 진단 0건이다. 자동 시험은 실제 청음·진동 검증을 대신하지 않는다.

## 초기 재연결 계획과 현재 남은 검증

1. 실제 휴대폰의 앱 설정에서 효과음·BGM·볼륨·진동 모드·저장 오류를 먼저 읽는다.
2. 현재 진동 모드의 재생 차단과 소리 모드를 한 변수씩 비교한다. 시스템 벨소리 모드 변경에 관한 사용자 응답은 대기 중이며 임의로 바꾸지 않았다.
3. 최신 코드로 뽑기를 재생하면서 해당 개발 앱의 오디오 상태·진동 요청 처리를 확인하고, 사용자의 청음·진동 체감 응답을 별도로 받는다.
4. 격리된 QA 데이터에서 남은 구매 복구·의상 저장·게임·미디어·기울임·접근성 검증을 진행한다. 글자·테마 등 임시 시험 설정은 원래 값으로 복원한다.

운영·시연 Android export는 아래 상태 문서의 최신 검증 결과를 따른다. 서명 APK/AAB 재빌드·공개 배포·Google Play는 이번 음악 수정의 검증 범위에 포함되지 않는다. README의 공개 기능·설치 안내는 바뀌지 않으므로 README 수정은 없다.

현재 앱 설정 조회와 소리 재검증은 위 최신 결과로 갱신됐다. 손에 든 준비 상태의 연속 진동 응답은 아직 없으므로 반복 진동을 보내지 않았다. 음악 PR #377은 병합 main `c7ac94af`에 포함됐지만 공개 APK 재빌드·배포 완료를 뜻하지 않는다.
